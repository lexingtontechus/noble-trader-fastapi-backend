## What "nothing survives" means — plain language

The heavy sweep's job is to pick the best SL/TP bracket for each symbol by
running a backtest over ~90 (brick_size × sl_bricks × tp_bricks) combinations
and ranking them by Sharpe. Once it has that ranking, Phase 3a's reachability
filter asks one additional question: **has this bracket's distance historically
produced trades that actually resolve, and does the realized expectancy justify
the risk?**

**Reachability** is about TP/SL hitting, not about the signal being correct.
It's `tp_bricks × brick_size / ATR` — how many ATRs away the TP is, which
directly governs whether price is likely to reach it within the 48-hour
expiry window. A bracket that requires price to travel 6× its daily range to
hit TP is geometrically unlikely to resolve before expiry. `bracket_reachability.py`
bins this ratio into five buckets:

| Bucket | What it means |
|---|---|
| 0.5-1 | TP is 0.5–1× ATR away — well within a day's range |
| 1-2 | TP is 1–2× ATR away — reachable in 1-2 days |
| 2-4 | TP is 2–4× ATR — a stretch in 48h |
| 4+ | TP is 4+ ATR away — rarely resolves before expiry |
| <0.5 | TP is so close it exposes more to noise; not generated by current grid |

Historical calibration in `nt_calibration_bias_by_bucket` shows whether trades
in each bucket actually closed at TP or SL (vs. expiring) and what the
expectancy was. The reachability filter keeps only the candidates whose bucket
has `expectancy_r > 0` in that historical record — scored-negative buckets are
excluded, unscored buckets are kept (fail-open).

**"Nothing survives"** means: the entire grid was evaluated, all ~90 combos
land in bucket 4+ for this symbol, and 4+ has negative historical expectancy
for this symbol. The filter correctly rejects all of them — but has nothing to
fall back to. The Sharpe-only baseline pick is kept (it's the live-mode
provisional fallback), but it's known to be in a bad bucket.

The root cause is that `generate_brick_sizes()` is **price-%-based**, not
ATR-anchored. For high-priced metals like XAUUSD/XAUEUR/XAUAUD:
`price × 0.40% / 100 × [0.75,1.0,1.5,2.0,3.0]` produces brick sizes in the
$8–$40 range. With `tp_bricks` minimum 4, the minimum TP distance is ~$32–160,
which at XAUUSD's typical ATR (~$25–35) is already 4+ ATR territory. The grid
never generates a candidate below that ratio regardless of which (sl, tp)
combination is tried — so the reachability filter can't help no matter how
good it is.

widened grid would have picked; in `live`, the widened pick becomes the real
pick when it exists.

## Phase 3b activation plan — 4 steps

### Step 1 — Flip `heavy_sweep_atr_anchored_bricks_mode` to `shadow` (no code needed)

Single YAML edit: `config/feature_flags.yaml` line
`heavy_sweep_atr_anchored_bricks_mode: "off"` → `heavy_sweep_atr_anchored_bricks_mode: shadow`.

What happens:
- Every heavy sweep (weekly cron + emergency sweeps) backtests the 3 ATR-anchored
  candidates alongside the existing 5 price-%-based ones.
- `select_best_combo_with_atr_anchoring()` computes what the widened grid
  would have picked, records it in `nt_heavy_sweep_atr_anchored_shadow`
  (baseline pick, widened pick, whether they differ, what bucket each is in).
- The **real** `brick_params.yaml` pick is **unchanged** — restricted to original
  5 brick sizes only in shadow mode. Zero live-behavior change.

`nt_heavy_sweep_atr_anchored_shadow` is empty now; it starts populating from
the first heavy sweep after the restart.

**Suggested: do this in this session** — there is no build work, it's a YAML
edit, and 3 weeks of `nt_heavy_sweep_reachability_shadow` data says the
"nothing survived" pattern is real and persistent. Waiting more doesn't produce
better evidence for whether to activate shadow.

### Step 2 — Stage 1 review: does the widened grid land in a better bucket?

Review criterion (from worklog 20260907, Stage 1):

> For every symbol where `n_changed` is a meaningful fraction of `n_compared`,
> confirm `last_widened_bucket` shows `expectancy_r > 0` in
> `nt_calibration_bias_by_bucket` and is narrower than the baseline bucket.

**Mechanical query**:
```sql
select
    s.symbol,
    s.n_compared,
    s.n_changed,
    s.last_baseline_bucket,
    s.last_widened_bucket,
    b.expectancy_r  as widened_exp_r
from nt_heavy_sweep_atr_anchored_shadow s
left join nt_calibration_bias_by_bucket b
    on b.symbol = s.symbol
    and b.distance_atr_bucket = s.last_widened_bucket
order by s.symbol;
```

Pass condition per symbol: `last_widened_bucket` ∈ {0.5-1, 1-2, 2-4} (narrower
than 4+) AND `widened_exp_r > 0` OR `widened_exp_r IS NULL` (unscored = fine).

**Sample-size bar**: `n_compared >= 10` before treating a symbol's pattern as
real (from worklog 20260907). XAUUSD/XAUEUR/XAUAUD have been averaging
0.6–0.9 heavy sweeps/week each (emergency sweeps included) — expect ~3-4 weeks
to clear 10 for most, possibly sooner for XAUAUD which has the lowest n_compared
(9) after 3 weeks (6 non-emergency runs likely).

**Stage 1 is global**: the flag applies to all symbols at once. A single symbol
that shows `last_widened_bucket` with negative expectancy blocks the flip for
all of them. If one symbol consistently fails while the rest pass, options are:
(a) investigate whether different ATR multipliers would help it, (b) accept the
flip with that symbol flagged for tight Stage 2 monitoring, or (c) wait.

**Target review date**: 2026-10-05 (~3 weeks from shadow activation) — enough
time for XAUUSD/XAUAUD to clear `n>=10` and for XAUEUR (already at 19
reachability runs) to have multiple ATR-anchored shadow comparisons.

### Step 3 — Flip `heavy_sweep_atr_anchored_bricks_mode` to `live`

Once Stage 1 review passes. Single YAML edit: `shadow` → `live`.

What changes: the widened pick (ATR-anchored bracket if better) is written to
`brick_params.yaml` and used for real signal generation. Still subject to the
full 7-gate qualification chain — this only changes *which bracket* is offered,
not whether it qualifies.

Rollback trigger: if any symbol's realized `expectancy_r` for its
ATR-anchored bracket comes in negative (first visible via `nt_calibration_bias_by_bucket`
weekly refresh), flip back to `shadow` immediately — YAML edit, no data loss,
no migration needed.

### Step 4 — Flip `heavy_sweep_reachability_mode` to `live`

Gated on Step 3 being live first. **This is the key sequencing constraint**:
`reachability_mode=live` before ATR-anchored bricks are live means "nothing
survived" symbols get the provisional fallback (Sharpe-only baseline pick
from the still-bad 4+ bucket) on every sweep. After Step 3, the widened grid
contains candidates in 0.5-1 / 1-2 buckets for XAUUSD/XAUEUR/XAUAUD — the
reachability filter now has something good to pick.

**Live-mode fallback decision (the open question from 20260825)**: when even
the widened grid finds nothing that clears the expectancy bar for a given sweep,
what does `reachability_mode=live` do? The provisional choice in the code is
already implemented: keep today's Sharpe-only pick rather than skip the sweep
outright (`heavy_sweep.py:999-1009`). This is the safer of the two options
(a symbol going a full week without a fresh combo is worse than one bad-bucket
sweep). That provisional code is already there — no build work needed, and it's
the right call.

### Open question needing a decision before Step 3

**USDCAD** has only "4+" calibration data — it will show "nothing survived"
simply because 4+ has negative expectancy, not because it needs ATR-anchored
bricks. ATR-anchored bricks *would* give it candidates in 0.5-1/1-2 buckets,
but those buckets have **no calibration data yet** (unscored = reachability
filter passes them = fail-open). So USDCAD might benefit from Step 3 for a
different reason: the ATR-anchored bracket may genuinely be better for it, but
the evidence won't be visible until Stage 2 outcomes accumulate. Worth flagging
at the Step 2 review: is USDCAD's widened pick landing in a bucket that's
genuinely promising (even if unscored), or just not-as-bad?

  written YAML unchanged.

  empirically (worklog 20260907). Don't re-tune without new evidence.
