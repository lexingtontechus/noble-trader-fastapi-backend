### 1\. Initial Setup: The BTC "Pilot" (1 Symbol, 2 Years)

To get started with BTC, you need a high-compute environment to handle the long-sequence processing of two years of data (approx. 17,500 hourly bars).

1. **Environment:** Use a **Lightning AI Pro T4 instance**. It provides 95 hours of GPU time, which is ideal for the 15-minute "heart-beat" polling required by the Noble system Conversation History.  
2. **Data Fetching:** Use the existing fetchSweepCandles() utility to pull 2 years of BTC hourly OHLCV data from HyperLiquid 1\.  
3. **The Learning Process:** TimesFM doesn't require "training" in the traditional sense for each asset; it uses **Zero-Shot Forecasting**. You provide the 2-year history as a "context window." The model "learns" the recent patterns in that window to predict the next 1–12 bars Conversation History.  
4. **Integration:**  
5. Pass the OHLCV array to the TimesFM /forecast endpoint.  
6. Map the output to a direction probability ($P\_{timesfm}$).  
7. Inject $P\_{timesfm}$ into the **EV Engine** as the P\_markov component (30% weight) 2, 3\.

### 2\. Scaling to 27 Symbols: The "Multi-Asset Pulse"

Transitioning from 1 to 27 symbols requires shifting from sequential processing to **vectorized batched inference** to stay within API rate limits and CPU budgets.

#### A. Batched Inference Logic

Instead of calling the model 27 times, modify the light-regime/index.ts edge function to:

1. **Aggregate Data:** Collect the latest 500–1000 bars for all 27 symbols (BTC, ETH, AAPL, Gold, etc.) into a single **3D tensor** (Shape: \[27, Horizon, Features\]) 4, 5\.  
2. **Single GPU Pass:** Send this tensor to your TimesFM service. Modern GPUs like the **NVIDIA T4** can process multiple time-series in parallel significantly faster than sequential API calls Conversation History.  
3. **Redis Broadcast:** Write the resulting $P\_{timesfm}$ scores to each symbol’s trading:config:{symbol} hash in Redis 6, 7\.

#### B. Managed Scheduling (Staggered Cron)

To avoid hitting the **130s deadline guard** on Supabase or overwhelming the backend, use the **staggered sub-batching** method already implemented for HMM detection 8, 9:

* **Sub-batches:** Group symbols into three sub-batches of 9\.  
* **Offset:** Run Sub-batch 1 at :00, Sub-batch 2 at :01, and Sub-batch 3 at :02.  
* **Frequency:** Maintain the **15-minute refresh rate** for the "Light Regime" to ensure the foundation model's context is never more than 15 minutes stale 5, 9\.

### 3\. Evolutionary Learning & Calibration

As you scale, the system uses the **Bayesian Updater** to "learn" how well TimesFM is performing for each specific asset class.

* **Weighting by Asset Class:** Your 27 symbols include diverse assets (Meme coins vs. Mega-cap stocks) 4\. TimesFM may be more accurate for trending assets like **SOL** (Sharpe 55.10) than mean-reverting ones like **USDCAD** (Sharpe 6.51) 10, 11\.  
* **Calibration Loop:** Use the CalibrationRecord schema to track predictedPWin vs. actual outcomes 12\. If TimesFM consistently over-predicts win rates for Forex but under-predicts for Crypto, you can dynamically adjust the signal weights ($w\_r, w\_i, w\_m$) per asset class in the EV Engine 3, 12\.  
* **Replacing Heavy Sweeps:** As of migration 026 (June 2026), heavy sweeps now run **weekends only** (2×/week). The TimesFM confidence gate skips ~70% of heavy HMM runs by checking forecast confidence first, and shift-aware wakeups trigger emergency heavy sweeps mid-week when volatility regimes change. This reduces heavy sweep compute by ~95% vs the original every-4-hour schedule.
