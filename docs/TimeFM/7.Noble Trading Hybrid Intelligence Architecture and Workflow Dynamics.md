The hybrid intelligence architecture of the Noble Trading platform utilizes a tiered workflow to balance structural stability with real-time market adaptation. This system orchestrates data and signals across **Supabase**, **FastAPI**, **TimesFM**, and **Redis**.

### 1\. Heavy Sweep Workflow (Structural Calibration)

**Frequency:** Every 4 hours per symbol 1, 2\.**Purpose:** Re-optimizing core parameters (brick size, SL, TP) to ensure they remain synchronized with evolving market microstructures Conversation History.

1. **Supabase (The Scheduler):** The pg\_cron extension triggers the heavy-sweep Edge Function according to a staggered schedule to avoid API rate limits 1-3.  
2. **Supabase Edge Function (The Orchestrator):**  
3. Fetches 45–90 days of historical hourly bars from Yahoo Finance or HyperLiquid 4, 5\.  
4. Calculates ATR-based brick size multipliers 4, 6\.  
5. Dispatches a parallelized request (Promise.allSettled) to the FastAPI backend 4\.  
6. **FastAPI Backend (The Optimizer):**  
7. Executes a full grid search (typically 72+ combinations) across brick sizes, stop-losses, and take-profits 4, 7\.  
8. Identifies the "Sharpe-optimal" configuration while applying overfit guards (e.g., rejecting Sharpe \> 10\) 1, 4, 6\.  
9. **Redis (State Persistence):** The Edge Function writes the finalized "Golden State"—including the optimized brick parameters and initial EV state—to the trading:config:{symbol} hash 1, 4, 8\.  
10. **Supabase Database (The Ledger):** Logs the comprehensive results of the sweep into the sim\_sweep\_results table for historical performance auditing 1, 9\.

### 2\. Light Regime Workflow (Real-Time Adaptation)

**Frequency:** Every 15 minutes per symbol 10, 11\.**Purpose:** High-frequency adaptation to the current market environment (volatility and trend) without changing underlying strategy parameters Conversation History.

1. **Supabase (The Scheduler):** Triggers the light-regime Edge Function in 3-symbol sub-batches with 1-minute gaps to prevent overwhelming the Edge Runtime worker pool 11, 12\.  
2. **TimesFM (The Foundational Prior):**  
3. The Edge Function aggregates recent bars for all symbols into a single 3D tensor 13\.  
4. The **TimesFM Inference Service** (hosted on a GPU node like Lightning AI) performs a single batched pass to provide a foundation-scale directional forecast 275, 278, Conversation History.  
5. This zero-shot forecast ($P\_{timesfm}$) replaces or supplements the current heuristic $P\_{markov}$ in the Bayesian Updater 274, Conversation History.  
6. **FastAPI Backend (The Detection Engine):**  
7. Runs fast HMM-only detection to classify the market into one of **5 trend states** and **2 volatility states** 10, 14\.  
8. Calculates the **Blended $P\_{win}$** by weighting HMM posteriors (40%), L2 imbalance (30%), and the TimesFM-enhanced Markov prior (30%) 192, 211, 229, Conversation History.  
9. **Redis (Golden State Update):** Refreshes the trading:config:{symbol} hash with the latest regime label, confidence score, EV-scaled Kelly size, and aggression level (Passive/Mid/Aggressive) 10, 12, 15\.  
10. **Supabase Database (Shift Tracking):** If the current regime differs from the previous one, it logs a **Regime Shift** to the sim\_regime\_log table, which can trigger defensive measures like auto-closing positions 10, 16, 17\.
