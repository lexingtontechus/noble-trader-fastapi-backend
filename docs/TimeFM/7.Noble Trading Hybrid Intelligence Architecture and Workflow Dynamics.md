The hybrid intelligence architecture of the Noble Trading platform utilizes a tiered workflow to balance structural stability with real-time market adaptation. This system orchestrates data and signals across **Supabase**, **LightningAI (SweepOrchestrator)**, **TimesFM**, and **Redis**.

> **NOTE:** Supabase Edge Functions (Deno) as the sweep engine are **deprecated**. The Python `SweepOrchestrator` running on **LightningAI** is now the unified engine. Supabase PostgreSQL remains the system-of-record for symbols, cron schedules, and sweep history.

### 1\. Heavy Sweep Workflow (Structural Calibration)

**Frequency:** Every 4 hours per symbol (weekends only, per `regime_cron` in `nt_symbol`) 1, 2. **Purpose:** Re-optimizing core parameters (brick size, SL, TP) to ensure they remain synchronized with evolving market microstructures.

1. **Supabase (The Data Store):** Holds the `nt_symbol` table with per-symbol `regime_cron` schedule values and sweep history in `nt_sweep_results`.  
2. **LightningAI — SweepOrchestrator (The Engine):** Reads active symbols and their cron schedules from Supabase. APScheduler triggers sweep groups on the configured schedule.  
3. Fetches 45–90 days of historical hourly bars from Yahoo Finance or HyperLiquid.  
4. Calculates ATR-based brick size multipliers.  
5. **HMM Regime Detection + Kelly Sizing + EV Engine** run inside the orchestrator.  
6. **Redis (State Persistence):** The orchestrator writes the finalized "Golden State"—including the optimized brick parameters and EV state—to the `trading:config:{symbol}` hash as a pipelined HSET + EXPIRE.  
7. **Redis Pub/Sub:** `PUBLISH agent:{symbol}` pushes the heartbeat/signal payload to subscribed DOOM agents.  
8. **Supabase Database (The Ledger):** Logs the comprehensive results of the sweep into `nt_sweep_results` for historical performance auditing.

### 2\. Light Regime Workflow (Real-Time Adaptation)

**Frequency:** Every 15 minutes per symbol (per `regime_cron` in `nt_symbol`) 10, 11. **Purpose:** High-frequency adaptation to the current market environment (volatility and trend) without changing underlying strategy parameters.

1. **Supabase (The Data Store):** Symbol registry and schedule source; the orchestrator reads cron schedules directly from `nt_symbol.regime_cron`.  
2. **TimesFM (The Foundational Prior):**  
3. The **TimesFM Inference Service** (hosted on a GPU node on Lightning AI) performs batched inference to provide a foundation-scale directional forecast.  
4. This zero-shot forecast ($P\_{timesfm}$) replaces or supplements the current heuristic $P\_{markov}$ in the Bayesian Updater.  
5. **LightningAI — SweepOrchestrator (The Engine):** Runs fast HMM detection to classify the market into regime states, computes blended P_win, Kelly sizing, and EV.  
6. **Redis (Golden State Update):** Writes `trading:config:{symbol}` (pipelined HSET + EXPIRE with 1h TTL), `trading:heartbeat:{symbol}` (SET with per-symbol TTL), and `PUBLISH agent:{symbol}` — all in a single pipeline round-trip.  
7. **Supabase Database (Shift Tracking):** If the current regime differs from the previous one, it logs a **Regime Shift** to `nt_regime_log`, which can trigger defensive measures like auto-closing positions.

### Summary of Platform Roles

| Platform | Role in Heavy Sweep | Role in Light Regime |
|---|---|---|
| **Supabase** | Stores symbol registry, cron schedule, logs optimized params | Stores symbol registry, cron schedule, logs regime shifts |
| **LightningAI (SweepOrchestrator)** | Full sweep: HMM + Kelly + EV + grid search + Redis writes + pub/sub | Fast HMM detection, EV blending, Kelly sizing, Redis writes + pub/sub |
| **FastAPI Backend** | Optimizer utilities (shared EV engine, position sizer) | Detection engine, WebSocket feeds, API endpoints |
| **TimesFM** | N/A (heavy sweep uses historical bars) | Provides "Zero-Shot" directional priors to eliminate 200-bar warm-up |
| **Redis** | Stores single source of truth config (1h TTL) + pub/sub heartbeat | Updates live conviction signals and aggression levels (1h TTL) + pub/sub heartbeat |
