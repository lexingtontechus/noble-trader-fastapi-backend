Based on the documentation for the **Noble Trading App**, the required database schema is designed to support a two-tier intelligence system, multi-venue execution, and a self-correcting calibration loop 1-3.  
The following schema is structured into three primary categories: **Core Intelligence**, **Execution & Journaling**, and **System Administration**.

### 1\. Core Intelligence Tables

These tables manage the symbol registry, optimization history, and real-time market state logs.

#### nt\_symbols — Symbol Registry

### 3\. System & Admin Tables

#### nt\_renko\_snapshot — Warm-up Cache

Persists the Renko pipeline state so returning users see instant charts 15\.

* **Columns:** symbol (PK), brick\_size (PK), bricks (JSONB), signals (JSONB), trades (JSONB), updated\_at (TIMESTAMPTZ) 15, 16\.

#### nt_system\_config — Runtime Settings

Stores dynamic settings like sizing\_mode (Kelly vs. Masaniello) and risk thresholds 17, 18\.

* **Columns:** config\_key, config\_value, updated\_at.

#### Venue — Venue Registry

* **Columns:** id, name (hyperliquid/alpaca), venueType (perp\_futures/equities), supportsStops, maxLeverage, isActive 19, 20\.

### Implementation Note

The backend utilizes **Prisma ORM** with **PostgreSQL (Supabase)** for persistent storage 9, 21\. For time-sensitive configuration and the "Golden State," **Upstash Redis** is used to store trading:config:{symbol} hashes for immediate access by the trading bot 22, 23\.
